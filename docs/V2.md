# Zenhance v2 — the canvas map

> **Status:** direction agreed, feel study built and verified (`app/lab/canvas`). No production code changed yet.
> **The story-by-story build plan lives in [V2-BUILD-PLAN.md](V2-BUILD-PLAN.md)** — read that before writing code.
> **Trigger:** Greg's prototype — a working React + Konva build of the same product, kept at
> [`reference/greg-preview-v1.html`](reference/greg-preview-v1.html) (open it with `file://`; see that
> directory's README for what it demonstrates).

## Why v2 exists

Greg's preview is not a mockup. It is a bundled React 18 + **Konva** app: a free-form spatial canvas with a
four-rung semantic-zoom ladder, on-map editing, drawable zones, layer toggles and a hypothetical mode. It
looks and feels better than `/org` for two structural reasons, neither of which is a styling problem:

1. **It renders to canvas.** Pan, pinch and node-drag stay smooth at a node count where SVG + `d3-zoom`
   starts dropping frames — which is exactly the "SimCity for a COO on an iPad" bar in [ROADMAP.md](ROADMAP.md).
2. **Position is data, not layout output.** You put Atlas over *there* and it stays there. The radial map's
   positions are computed by `d3.tree()` every render, so spatial memory is impossible by construction — the
   thing that makes a map feel like *your* map.

Everything else that impresses in his build (zones, the zoom ladder, inline editing) is downstream of those two.

| Theme | The light/flat/calm "paper" register — this settles the **Mini Metro theme** story in ROADMAP.md. **Scope revised: the *whole app* moves to paper**, not just the map. The 5 existing palettes become accents over a shared paper base rather than whole dark themes. | **revised 2026-08-25** |
| Sequencing | **Foundation, but front-load the look** — build the real persistence/adapter seam, and pull the paper theme + zoom ladder forward so every intermediate state is demo-able. | 2026-08-25 |
| Top rung: are groups placeable? | **Placeable, with centroid fallback.** A group can be dragged and its position persists; with no stored row it renders at the centroid of its placed children. One consistent `stored ?? computed` rule for every node type. | 2026-08-25 |

## What changes architecturally

- **Positions become persisted, per-workspace data.** Recommended: a `map_nodes` table
  (`workspace_id`, `board_id`, `node_type`, `node_id`, `x`, `y`) rather than `x`/`y` columns on `people` /
  `org_units` — it keeps the core tables clean and leaves room for multiple boards and saved scenarios.
  A missing row falls back to a seeded layout, so import and demo orgs still work on first open.
- **A flat node list replaces the hierarchy as the render input.** The tree still exists in the data; the
  canvas just doesn't lay out *from* it. See `app/lab/canvas/demoMap.ts` for the shape.
- **Zones need their own table** (`map_zones`) once they persist.
- **Colour tokens need a JS bridge.** Palettes live in CSS vars (`app/globals.css` `@theme static`); canvas
  draws with JS values and cannot read them. Expect a resolved-palette hook or a JS-side palette table.
- **Accessibility regresses unless designed for.** Canvas has no DOM, so the current keyboard/screen-reader
  surface disappears. The map needs a parallel accessible outline (the existing `orderedUnitTree` helper in
  `lib/org/model.ts` is the obvious source).

**The rule that makes V2.0 cheap:** a missing `map_nodes` row is a *computed fallback*, not an error —
person/team fall back to `seedLayout()`, a group to the centroid of its placed children. So no write ever
happens on a page read, a freshly imported org renders with zero rows, and `seedLayout()` is the same pure
function that becomes "Tidy up".

## What the lab proved

`app/lab/canvas` (`/lab/canvas`) is a working feel study on a client-side copy of the real demo org —
55 nodes, 3 release trains, the cross-cutting supporters, real costs and allocations. Verified headless:

| Zoom | Rung | |
|---|---|---|
| 0.13× | Trains | five cluster marks, headcount + monthly cost |
| 0.28× | Squads | squad circles inside train hulls, FTE + "n short" |
| 0.61× | People | person dots, delivery edges appear |
| 1.86× | Roles | title + delivery load % per person |

Also working: free-form drag, drop-a-person-on-a-squad to move their majority seat (with Undo),
delivery/reporting layer toggles, search-with-halo, and **zones** — drag a box, get people / squads / FTE /
monthly cost / over-allocated / open roles for whatever is inside it.

**Deliberately not in the lab:** persistence, real data, analytics overlays, the findings rail, scenario
mode, on-map editing, place-node tools, accessibility. Those are the staged plan above, not the feel study.

## Open questions for the design pass

- ~~Does the top rung stay computed clusters, or do trains become placeable nodes?~~ **Answered 2026-08-25** — placeable, centroid fallback (see decisions table).
- Do zones persist as org artifacts ("the Atlas cutover"), or stay ephemeral like a marquee selection? *(due in S6; V2-BUILD-PLAN proposes persist)*
- What does "Tidy up" do to positions a user has deliberately arranged — replace, or offer a preview? *(due in S5; V2-BUILD-PLAN proposes replace + single-level Undo)*
- Free drag repositions, but drop-onto-a-squad reassigns — the same gesture. How do they disambiguate? *(due in S4)*
- The four-rung ladder assumes exactly group→team→person. What happens when sub-groups (teams-of-teams) land? *(bind rungs to tree role, not literal depth — decide before seeding nested demo data)*
