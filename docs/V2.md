## Why v2 exists

Greg's preview is not a mockup. It is a bundled React 18 + **Konva** app: a free-form spatial canvas with a
four-rung semantic-zoom ladder, on-map editing, drawable zones, layer toggles and a hypothetical mode. It
looks and feels better than `/org` for two structural reasons, neither of which is a styling problem:

1. **It renders to canvas.** Pan, pinch and node-drag stay smooth at a node count where SVG + `d3-zoom`
   starts dropping frames — which is exactly the "SimCity for a COO on an iPad" bar in [ROADMAP.md](ROADMAP.md).
2. **Position is data, not layout output.** You put Atlas over *there* and it stays there. The radial map's
   positions are computed by `d3.tree()` every render, so spatial memory is impossible by construction — the
   thing that makes a map feel like *your* map.

Everything else that impresses in his build (zones, the zoom ladder, inline editing) is downstream of those two.

## Decisions taken

| Question | Decision |
|---|---|
| Replace or coexist? | **Canvas becomes the `/org` default. Radial survives as a view mode** — its `d3.tree()` output becomes the "Tidy up" command that *writes* positions. Nothing shipped gets thrown away. |
| Renderer | **Konva + react-konva**, as Greg used. Already added to `package.json`. |
| Theme | The light/flat/calm "paper" register — this settles the **Mini Metro theme** story in ROADMAP.md. |

## What changes architecturally

- **Positions become persisted, per-workspace data.** Recommended: a `map_nodes` table
  (`workspace_id`, `board_id`, `node_type`, `node_id`, `x`, `y`) rather than `x`/`y` columns on `people` /
  `org_units` — it keeps the core tables clean and leaves room for multiple boards and saved scenarios.
  A missing row falls back to a seeded layout, so import and demo orgs still work on first open.
- **A flat node list replaces the hierarchy as the render input.** The tree still exists in the data; the
  canvas just doesn't lay out *from* it. See `app/lab/canvas/demoMap.ts` for the shape.
- **Zones need their own table** (`map_zones`) once they persist.
- **Colour tokens need a JS bridge.** Palettes live in CSS vars (`app/globals.css` `@theme static`); canvas
  draws with JS values and cannot read them. Expect a resolved-palette hook or a JS-side palette table.
- **Accessibility regresses unless designed for.** Canvas has no DOM, so the current keyboard/screen-reader
  surface disappears. The map needs a parallel accessible outline (the existing `orderedUnitTree` helper in
  `lib/org/model.ts` is the obvious source).

## Staged plan

**V2.0 — viewport. ✅ Shipped.** `components/viz/OrgCanvas.tsx` behind `?view=canvas` on `/org`, reading
the real snapshot from `getOrgSnapshot`. `map_nodes` schema + migration; seed positions come from
`lib/canvas/buildCanvasMap.ts` — a deterministic nested-ring layout (value streams gridded, squads ringed around
their value stream, people ringed around their home squad), the same shape the lab proved rather than a literal
reuse of `RadialOrg`'s per-focus `d3.tree()` (which has no single full-org layout to borrow); persisted on
drag end via `saveMapNodePosition`. Ships pan / pinch / zoom, the four-rung ladder, and selection with new
`PersonBody` / `SquadBody` panels (RadialOrg's `UnitPanel` / `PersonPanel` are tightly coupled to its
drill-down `NodeDatum`, so these are parallel components over the flat `CanvasNode` shape, not a shared
import). **Deliberately deferred to V2.1/V2.2:** delivery/reporting edges, search, zones, drag-to-reassign,
scenario mode, analytics overlays — the lab has all of these; this pass intentionally didn't port them, to
keep the persistence + rendering foundation reviewable on its own.

**V2.1 — parity, then the switch.** Port the shipped analytics onto canvas: overlays
(`getOverlayProps`), the findings rail, scenario mode, drag-to-reassign, and search with an *additive halo*
(the ROADMAP records that dim-only was illegible on a touch glance — the lab already does the halo).
Make canvas the default; radial becomes a view mode + "Tidy up".

**V2.2 — the new capabilities.** Zones (the spatial-selection readout), delivery-vs-reporting layer toggles
(closes the backlog's edge-type story), ~~inline on-map editing~~, ~~place-new-node tools~~ (both shipped
early, v0.1.11 — see the S2 status note above), snap-to-grid.

**V2.3 — touch polish.** Bottom-sheet panel in portrait, ≥44px targets, the paper theme promoted to a real
palette in `lib/theme.ts`, and the accessible outline above.

## What the lab proved

`app/lab/canvas` (`/lab/canvas`) is a working feel study on a client-side copy of the real demo org —
55 nodes, 3 value streams, the cross-cutting supporters, real costs and allocations. Verified headless:

| Zoom | Rung | |
|---|---|---|
| 0.13× | Value streams | five cluster marks, headcount + monthly cost |
| 0.28× | Squads | squad circles inside value stream hulls, FTE + "n short" |
| 0.61× | People | person dots, delivery edges appear |
| 1.86× | Roles | title + delivery load % per person |

Also working: free-form drag, drop-a-person-on-a-squad to move their majority seat (with Undo),
delivery/reporting layer toggles, search-with-halo, and **zones** — drag a box, get people / squads / FTE /
monthly cost / over-allocated / open roles for whatever is inside it.

**Deliberately not in the lab:** persistence, real data, analytics overlays, the findings rail, scenario
mode, on-map editing, place-node tools, accessibility. Those are the staged plan above, not the feel study.

## Open questions for the design pass

- Does the top rung stay computed clusters (value stream centroids), or do value streams become **placeable nodes** too?
- Do zones persist as org artifacts ("the Atlas cutover"), or stay ephemeral like a marquee selection?
- What does "Tidy up" do to positions a user has deliberately arranged — replace, or offer a preview?
